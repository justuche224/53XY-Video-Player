## 1. What this app is

**53XY** is an Android-first, "best of all worlds" local video player built with **Expo SDK 56 / React Native 0.85**. The full vision is in [00-vision-and-context.md](./00-vision-and-context.md). In short: take the best of VLC + MX Player and fix what they get wrong — smart auto-grouping, folder view, resume + progress, long-press-to-2×, double-tap-seek, swipe brightness/volume, advanced filters — with a **beautiful Material You UI** and smooth, satisfying animations.

### Current capabilities
- **Library:** device scan → folder/title/episode parsing → grouping engine → adaptive grid/list UI, Videos/Folders tabs, search, group detail, thumbnails, multi-thumbnail collages, FlashList recycling, duration badges, empty states, android ripples.
- **Player:** `expo-video` playback, custom Reanimated/gesture-handler control overlay, auto-resume + snackbar, progress writes, orientation, keep-awake, next/prev in group, subtitle/audio tracks, pitch-preserved speed, replay-at-end fix. Gestures: long-press→2× (with haptics), 3-zone double-tap (back/play-pause/forward), swipe brightness (left) / system volume (right), horizontal drag-scrub, lock overlay. Background audio play and automatic PiP on swipe-home (toggled via Settings).
- **Filters & sort:** persistent min/max duration ignore, filename pattern ignore (substring/glob), folder ignore, composed `applyFilters`; sort by name/length/date-added/date-modified.
- **History & resume:** YouTube-style Watch History screen (day-bucketed, search, swipe-remove, clear-all, tap-to-resume); home-screen Resume FAB (most-recent existing video, group context for next/prev).
- **Infra:** Material You theming, SQLite + 3 migrations, shared library cache (`LibraryProvider`), dynamic `app.config.ts` with dev/preview/prod build variants (side-by-side installs), EAS profiles incl. `production-apk`.
- **Moments (capture only, Phase 1):** a bookmark button in the player's top bar captures the exact on-screen frame — position, a cleaned-up title/episode label, and a note seeded from the on-screen subtitle line — into `moments` (migration v11), with frames + a `moments.json` manifest written to `/storage/emulated/0/53XY/Moments` behind a `.nomedia`. A confirmation snackbar with an **Edit** action opens a note sheet. No browse/playback screen yet — see What's next.

- ✅ **Playback startup latency — fixed and device-verified (including scrubbing).** See [2026-08-26-playback-startup-latency.md](./2026-08-26-playback-startup-latency.md). Root cause: some 10-bit HEVC (Main10) `.mkv` files took 7–12s to start because ExoPlayer's `MatroskaExtractor` reads the file's `Cues` element (near EOF in these remuxes) via ~1-4 byte `DataSource.read()` calls — one file took 558,146 individual reads to move 781KB, ~12.8s purely from per-call overhead. A first fix (`FLAG_DISABLE_SEEK_FOR_CUES`, skip reading Cues entirely) fixed the speed but broke scrubbing — with no Cues, ExoPlayer has no seek index and any seek resolves to position 0 ("video starts afresh") — and was reverted. The real fix wraps the `DataSource` with a 64KB read-ahead buffer (`BufferedDataSource` in `DataSourceUtils.kt`) so those tiny sequential reads are served from an already-fetched chunk instead of a fresh read each time — `MatroskaExtractor`'s own Cues parsing and seeking are untouched. Patched via `patch-package` (`patches/expo-video+56.1.4.patch`, one file). Device-verified: fast start (well under 1s) **and** correct scrub-bar/swipe seeking on the same files. Note: expo-video ships a prebuilt AAR by default (`node_modules/expo-video/local-maven-repo/`) that Gradle links against instead of compiling `android/src` — patching the source alone does nothing until `expo.autolinking.buildFromSource: ["expo-video"]` is added to `package.json` (now is) to force a from-source build.

## 4. Architecture & gotchas

### Key files
- **Data:** `src/db/` (schema/migrations, videos-repo, progress-repo, settings-repo, progress math), `src/media/` (media-scanner, derive-folder, thumbnails).
- **Grouping engine** (pure, tested): `src/library/normalize-title.ts`, `parse-episode.ts`, `group-videos.ts` (conservative numeric merge), `filter-groups.ts`, `episode-label.ts`.
- **Filters** (pure, tested): `src/library/filter-videos.ts` (length + name-pattern + folder; composed `applyFilters`).
- **Sort** (pure, tested): `src/library/sort-groups.ts` (`sortGroups`, nulls-last).
- **History** (pure, tested): `src/history/bucket-day.ts`, `assemble-history.ts`.
- **Resume** (pure, tested): `src/player/resume-last.ts` (`resolveLastPlayed`).
- **Hooks:** `src/library/use-library.ts` (cache-first + background rescan), `use-groups.ts` (read-only, for detail).
- **Player:** `src/app/player.tsx` + `src/components/player/` (overlay, gestures, lock) + `src/player/` (format-time, resume, playlist `neighbors`, progress-writer, seek, pan).
- **UI:** `src/app/` (index = library, group.tsx, player.tsx, history.tsx, settings.tsx, _layout.tsx = providers + error boundary), `src/components/` (group-card, group-row, episode-row, thumbnail-collage, video-thumbnail, progress-bar, pressable-scale, segmented-tabs, layout-toggle, search-bar, screen, resume-fab), `src/theme/` (Material You provider + token resolver).

### Key facts
- **`AGENTS.md`: Expo HAS CHANGED — read https://docs.expo.dev/versions/v56.0.0/ before writing any SDK code.** Verify against installed `node_modules/<pkg>/build/types/*.d.ts` when docs are thin.
- **Package manager is `bun`** (`bun.lock`). Use `npx expo install` for Expo deps; `bun add` for others. Tests/typecheck: `npm test`, `npx tsc --noEmit`.
- **expo-media-library SDK 56 is class-based**: `new Query().eq(AssetField.MEDIA_TYPE, MediaType.VIDEO).orderBy(AssetField.CREATION_TIME).exe()` → `Asset[]`; `await asset.getInfo()` returns metadata in one call; **`duration` is in milliseconds**; `uri` is a `file://` path (folder derived from it). Legacy `getAssetsAsync` is deprecated/throws.
- **`tsconfig.json` sets `types: ["jest","node"]`** — needed for jest globals; disables auto-@types inclusion — add new @types here if a dep needs ambient globals.
- **Typed routes** (`experiments.typedRoutes`): `.expo/types/router.d.ts` is gitignored and regenerated by `expo start`. After adding a new route file, `tsc` may complain until expo regenerates it.
- **Android-only.** `/android`, `/ios`, `.expo/` are gitignored (CNG — regenerated by prebuild/start).
- **Run/build:** `npx expo start` (JS reload, for JS-only changes) or `npx expo run:android` (full rebuild, when native modules change). `npm start`/`npm run android` set `APP_VARIANT=development` for the local dev variant.
- **`android/` is generated and goes STALE — `run:android` does not regenerate it.** `/android` is gitignored (CNG), and `npx expo run:android` reuses an existing `android/` rather than re-running prebuild. So anything added to `app.config.ts` *after* that directory was generated — permissions especially — never reaches a local dev build, while EAS (which prebuilds fresh every time) gets it. This bit us for real: `MANAGE_EXTERNAL_STORAGE` was added 2026-08-16 for all-files access, the local `android/` dated from 2026-07-31, and the dev APK simply did not declare the permission. Production did, so "it works on my other build" was actively misleading, and the failure showed up as a silently unwritable directory. **After changing anything in `app.config.ts`, regenerate with the variant set:** `APP_VARIANT=development npx expo prebuild --clean -p android`, then `npm run android`. Omitting `APP_VARIANT` bakes the *production* package id into the dev project. Verify a permission actually landed with `adb shell dumpsys package <pkg> | grep -A40 'requested permissions:'`, not by reading `app.config.ts`.
- **Dev and production install side by side, and system permission screens do not disambiguate them well.** `53XY` and `53XY (Dev)` are separate packages with separate grants; granting All-files access to one does nothing for the other. Never derive the package id from `Constants.expoConfig?.android?.package` for a deep link — the Metro server evaluates `app.config.ts` with whatever `APP_VARIANT` it was started with, so a dev build served by a plain `npx expo start` reports the production id. Use `expo-application`'s `Application.applicationId`, which is the real running process id.
- **App config & build variants:** config lives in **`app.config.ts`** (dynamic — no `app.json`). Package id + app name switch on `APP_VARIANT`: dev → `com.jvstuche.fiftythreexy.dev` "53XY (Dev)", preview → `…preview` "53XY (Preview)", prod → `com.jvstuche.fiftythreexy` "53XY". `eas.json` sets `APP_VARIANT` per profile. **Editing the EAS `projectId` must be done by hand** in `app.config.ts` (`extra.eas.projectId`) — `eas init` does NOT auto-edit dynamic configs. Profiles: `development`, `preview` (APK), `production` (AAB), `production-apk` (sideloadable APK). EAS owner `justuche224`, projectId `bfc694a1-7674-4389-a33d-45206bfbe9e8`.
- **FlashList is native** → changes that re-touch it need `npx expo run:android`.
- **`patch-package` is set up** (`postinstall` script, `patches/` dir) for patching third-party native modules directly — first use is `patches/expo-video+56.1.4.patch` (real fix, see [2026-08-26-playback-startup-latency.md](./2026-08-26-playback-startup-latency.md)). Generating a *new* patch needs `npx patch-package <pkg>`, which requires an npm/yarn lockfile to resolve a pristine copy — this project uses bun, so there is none; patches are hand-built as a `git diff --no-index` between a saved original and the edited file rather than introducing an npm/yarn lockfile. Applying patches (`postinstall`) does NOT hit that lockfile check and works fine with `bun install`.
- **The `moments` table has no FK to `videos`, on purpose.** `deleteVideosByIds` runs whenever a library scan finds a file gone, and both `playlist_items` and `manual_groups` cascade off `videos`. A moment has to outlive its file — that's the entire point of the feature — so it stores its own snapshot (title, episode label, filename, folder, video uri, duration) instead of joining live.
- **`FrameGrabber.grabFrame` takes an `exact?: boolean` option** that uses `MediaMetadataRetriever.OPTION_CLOSEST` instead of the default `OPTION_CLOSEST_SYNC`. It's slower (decodes forward from the preceding keyframe) and only needed when one specific frame matters — `OPTION_CLOSEST_SYNC` snaps to the nearest keyframe, which at a typical 5–10s GOP can be a different shot entirely. Thumbnail/scrub-preview callers don't pass it and keep the fast path.
- **`expo-file-system`'s `File.text()` is `Promise<string>`, not synchronous** — `File.textSync()` is the sync counterpart. Code with a synchronous signature that calls `.text()` will `JSON.parse` a `Promise` object, throw, and silently degrade rather than fail loudly. This cost real debugging time once (`src/moments/storage.ts`'s manifest read); verify sync-vs-async against `node_modules/expo-file-system/build/*.d.ts` before assuming, for any new expo-file-system code.
- **Expo modules can ship a prebuilt AAR instead of building from source.** Any package with a `local-maven-repo/` dir under its `node_modules/<pkg>/` (check `find node_modules -maxdepth 2 -iname local-maven-repo`) gets linked as that prebuilt binary by default — Gradle never touches `android/src`, so a `patch-package` edit to that module's Kotlin/Java silently does nothing. Force a from-source build (needed for any native patch to take effect) via `package.json`: `"expo": { "autolinking": { "buildFromSource": ["<pkg-name>"] } }`. Verify a patch actually compiled in by grepping the built APK's dex for a string unique to the patch (`unzip -p app-debug.apk classes.dex | strings | grep <marker>`) — a green Gradle build proves nothing about which source Gradle actually used.

### Player gotchas (learned on-device)
- **`useVideoPlayer({ uri })` recreates the player whenever `uri` changes** (keyed on `JSON.stringify(source)`). Switch videos by changing the `uri` route param (`router.setParams`), NOT `player.replace`; key subscription + resume effects on `[player]` so they re-bind.
- **Flush progress from cached position/duration refs, never `player.currentTime`** — expo-video releases the player before unmount cleanup runs ("Cannot use shared object that was already released").
- **Player chrome must be fixed white**, not theme `onSurface` (near-black on dark video under a light theme); wrap controls in safe-area insets.
- **Library lists refetch progress via `useFocusEffect`**, so resume bars update on return from the player.
- **Volume must use the system stream, not `player.volume`** — ExoPlayer's per-player volume corrupts audio. The local `modules/system-volume` Kotlin module sets `AudioManager.STREAM_MUSIC`. Worklet→JS hops use `scheduleOnRN` (not deprecated `runOnJS`); pure helpers are called on the JS thread, never inside a worklet. **Changes to `modules/system-volume` need `npx expo run:android`.**
- **SAF gives you a document id, not a filename** — `File.pickFileAsync` returns a `content://` URI whose last path segment is the provider's document id, and `File.name` is just that segment decoded. The external-storage provider's id happens to contain the path (`primary:Movies/Foo.srt`), so a real basename can be recovered; **the MediaStore provider's is a row number** (`msf:345000`), and the true `DISPLAY_NAME` is only reachable through a `ContentResolver` query — i.e. `expo-document-picker` or native code. **Decided: not worth a native dep for a label.** `subtitleDisplayName` (pure, Jest-tested) recovers the name where the URI carries it and falls back to the generic "Subtitle file" where it doesn't. Revisit only if a picker flow ever needs the filename for something load-bearing.
- **Chrome buttons overlap the gesture layer** — fixed via an RNGH gesture arena (`player-gesture-relations.ts` + `player-pressable-scale.tsx`'s `blocksExternalGesture`): chrome buttons win their own taps while double-tap side-seek still works with controls showing. Double-tap policy lives in pure `src/player/double-tap.ts` (`doubleTapAction`, Jest-tested): hidden overlay → left/center/right all act (center = play/pause toggle); visible overlay → left/right seek but center empty-space double-tap is a no-op.

## 7. Changelog

- **Playback startup latency — fixed (10-bit HEVC .mkv files)** — some files took 7–12s to start playback (vs. VLC's <500ms on the same file). A temporary I/O-tracing `DataSource` wrapper (added, then removed) found the actual cause: ExoPlayer's `MatroskaExtractor` reads the file's `Cues` element via ~1-4 byte reads — 558,146 individual reads to move 781KB in one trace, ~12.8s of pure per-call overhead. First fix attempt (`MatroskaExtractor.FLAG_DISABLE_SEEK_FOR_CUES`, skip reading Cues) fixed the speed but **broke scrubbing** (no Cues = no seek index = every seek lands on position 0) — reverted immediately. Real fix: `BufferedDataSource`/`BufferedDataSourceFactory` in expo-video's `DataSourceUtils.kt` wrap the real `DataSource` with a 64KB read-ahead buffer, so tiny sequential reads are served from memory instead of hitting the underlying source each time — `MatroskaExtractor`'s Cues parsing and seeking are completely untouched. Shipped via `patch-package` (`patches/expo-video+56.1.4.patch`). Required a second fix to actually take effect: expo-video ships a prebuilt AAR (`node_modules/expo-video/local-maven-repo/`) that Gradle links by default instead of compiling `android/src`, so `package.json` now sets `expo.autolinking.buildFromSource: ["expo-video"]` to force a from-source build. Device-verified: fast start **and** correct scrub-bar/swipe seeking together on the same files. tsc clean, 400 tests pass. See [2026-08-26-playback-startup-latency.md](./2026-08-26-playback-startup-latency.md). Not yet committed.

- **Shared group memoization (JS-only)** — the player screen called `useGroups(mode)` on every mount, re-deriving the full-library grouping from scratch even when the screen underneath (Home/group-detail) had just computed the identical result and was still mounted. `LibraryProvider` now computes `groupsByName`/`groupsByFolder` once (memoized on videos/manualGroups/filter) and `useGroups` is a plain selector over them. Found while investigating playback startup latency — see [2026-08-26-playback-startup-latency.md](./2026-08-26-playback-startup-latency.md); turned out to be real but not the dominant cost (the actual multi-second delay is native/ExoPlayer-side). tsc clean, 400 tests pass. Not yet committed.

- **Watched badge + boost-after-release fix (device-verified)** — a filled progress bar was the only sign a video had been finished, and it vanished the moment you replayed one. Root cause wasn't cosmetic: `watch_progress.completed` has existed since migration v1, but `upsertProgress` wrote `completed = excluded.completed`, so the first 5-second write of a replay **erased** the flag — which the UI never read anyway, deriving "watched" from `percent` alone. The flag is now sticky (`MAX(watch_progress.completed, excluded.completed)`), with Mark as unplayed — which deletes the row — the only reset; `ProgressEntry`/`HistoryRow` carry it, and `getProgressMap`/`getHistory` select it. **Migration v9** backfills `completed = 1 WHERE percent >= 0.95`, reconstructing the flag once for a library whose marks the old bug had cleared. UI: `WatchedBadge` (`checkmark-circle` on the same 62%-black chip as `DurationBadge`) pinned **top-right** — the only free corner, with duration bottom-right, the resume bar on the bottom edge and the selection check dead centre — and the progress bar is suppressed once watched, since a full bar under a check says the same thing twice. Group cards get the check only when *every* item is watched. This also collapsed a live inconsistency: `isCompleted` used 0.95 while `resolveWatchToggle` and `groupPercent` hardcoded 0.99; all three now read the one flag. Shipped alongside a **player crash fix**: `handleBoostEnd` wrote `player.playbackRate` from a gesture callback that can outlive the player — `useVideoPlayer` releases its shared object in the effect cleanup phase (uri swap on next/prev/autoplay, or unmount) while RNGH's `onFinalize` → `scheduleOnRN` hop lands the boost-end asynchronously after it, and **any call on a released shared object throws** (`SharedObject.release()` is documented as detaching JS from native; there is no `isReleased` flag to test first, so the throw is the only signal). Boost UI state now clears *before* the player is touched — a failed restore used to strand the 2× badge — and the restore swallows exactly the released-object error (`isReleasedObjectError`, pure + Jest-tested). The trigger, which is why it's near-impossible to reproduce on demand: a long-press that *spans* the switch — hold 2× as the video ends, the autoplay countdown swaps the video 5s later, then lift. JS-only.

- **Multi-file share (device-verified: 7 videos to LocalSend on SM-S901N with correct filenames/sizes, 3 to Quick Share on the emulator, 1-file share intact)** — "only 1 file can be shared at a time" wasn't a cautious guess, it was `expo-sharing`'s ceiling: `shareAsync(url: string)` takes one url and SDK 56 has no array form (the docs' only multi-file support, `multipleShareMimeTypes`, is for *receiving*). Sharing a selection therefore needs `ACTION_SEND_MULTIPLE`, which lives at the intent level — hence a third local Kotlin module, `modules/share-media`, alongside `system-volume` and `frame-grabber`. **The find that made it cheap:** `expo-media-library` asset ids on Android *are* MediaStore `content://` URIs (`build/types/Asset.d.ts` documents the constructor arg as such), and we already store the id on every video — so the intent carries them as-is, with no FileProvider config, no `file://`→`content://` conversion, no copying, and none of the percent-encoding/space-in-path trouble that cost the thumbnail engine half the library. The URIs also go into `ClipData`, not just `EXTRA_STREAM`: on several OEMs the extra alone grants read access to only the first item, which is the classic "receiver got 1 of 5 files" bug. Non-`content://` input throws a coded exception rather than surfacing as `FileUriExposedException` at runtime. Cap is **50, refused outright rather than trimmed** — a share is always exactly the selection or nothing, never a silent subset (pure `resolveShare`, Jest-tested). `expo-sharing` is now unused by the app but left installed. **Needs `npx expo run:android`** (new native module) — and note this rebuilt the *single*-file share path too, so verify that as well: 1 video to WhatsApp; 5 videos to WhatsApp (all 5 arrive); 5 to Drive/Files; 51 selected → refusal alert naming the cap; cancel the chooser → no crash.

- **Selection queueing (device-verified)** — closes the known gap left by the contextual-bar pass: "Play" now queues *exactly* the selected subset instead of starting at the earliest selected item and letting autoplay run through the whole group. - **Thumbnail extraction engine** — the black-tile bug is gone at the root: thumbnails were grabbed at a hardcoded `time: 1000`, one second in, where almost every episode is still on black or a fade-in. A new local Kotlin module `modules/frame-grabber` (`MediaMetadataRetriever`) instead walks a candidate ladder at 25 / 45 / 12 / 65% of duration and stops at the first frame clearing a score built from mean luma (rejects black, fade, blown white) and luma std-dev (rejects flat logo cards) — typically one decode, worst case four, and it writes the best-scoring candidate anyway rather than leaving a blank tile. Frames are now correctly sized (640px cards, 1280px for the continue-watching hero) instead of full-resolution JPEGs at quality 0.5, and live in the **document** dir, not the OS-evictable cache. Migration **v7** adds `thumb_version` / `thumb_attempts` / `thumb_time_ms` and nulls every old thumbnail; a `THUMB_VERSION` constant re-invalidates on future algorithm changes without another migration. Generation stays visible-first, plus a background sweep (`useThumbnailSweep`) that fills the rest of the library recently-played-first, pausing while backgrounded or while the player is on screen, and giving up on a file after 3 attempts. The player's scrub-preview strip moved onto the same extractor at 320px, and `expo-video-thumbnails` was dropped entirely. All policy (ladder, staleness, sibling invalidation, sweep order) is pure and Jest-covered; Kotlin owns only pixels. **Gotcha worth remembering:** `expo-media-library` percent-encodes its `file://` uris, so any native consumer must `Uri.decode` the path after stripping the scheme — `Uri.parse().getPath()` decodes but also truncates at a `#`/`?` in a filename, and a raw un-decoded path misses every folder with a space in it (that bug cost ~49% of the library, all of WhatsApp included). `src/media/derive-folder.ts` decodes for the same reason. Device-verified: 569/569 videos, 0 failures. - **External subtitles** — `expo-video` can only expose tracks the media file already carries, so external subtitles are parsed and rendered by us: `src/subtitles/` holds pure, Jest-tested modules for SRT/WebVTT/ASS parsing (ASS as plain text — positioning and styling discarded), CP1252-fallback decoding for the many non-UTF-8 files in the wild, sibling-file ranking, and delay-aware cue lookup. `useSubtitles` drives a 150ms cue clock off `player.currentTime` (the player's own `timeUpdateEventInterval` of 1s is far too coarse) and only re-renders when the visible line changes. Auto-detect ranks `Movie.srt` > `Movie.en.srt` > `Movie.forced.srt` > prefix matches, plus any file in a `Subs/` subfolder when the folder holds exactly one video. Reading a non-media file on Android 13+ needs `MANAGE_EXTERNAL_STORAGE`, detected by probing a directory listing rather than with native code, with a rationale sheet and an `expo-intent-launcher` deep link to the toggle; the SAF picker still works if it is declined. Delay bar (±20s, 50ms steps) built on raw `Gesture.Pan` with `blocksExternalGesture`, placed like `AutoplayCard`. Migration v10 stores `subtitle_uri`/`subtitle_delay_ms` per video. **Known limitation, decided not fixed:** a file picked from the MediaStore provider shows as "Subtitle file" rather than its real name — see the SAF gotcha in §4. **Online subtitle download is deliberately deferred to its own spec.** Spec/plan: [external-subtitles-design](./superpowers/specs/2026-08-16-external-subtitles-design.md), [external-subtitles-plan](./superpowers/plans/2026-08-16-external-subtitles.md).
